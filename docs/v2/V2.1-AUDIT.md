tree `347793330dd9472e29b85a8aa93ebc8beb51e098`. The local checkout was verified

The pinned, previously successful workflow input remains Spotify **9.1.90**:
SHA-256 `409601a58953818eea17edb92963d10256ae6fcf00c69954105e5becc08ec296`.

Neither the bundle identifier nor signing identities, certificates or API keys are changed.

## Reproducible defects in the old code

- `filterCandidateSongs` started a lyrics request for every unresolved track without a bound.
- AI album translation sent an entire chunk through a different, multi-song streaming parser.
  It therefore did not use the working single-song JSON contract. One chunk failure stopped
  the album. This is a source-confirmed failure path, not proof that the user's API hit a rate limit.
- The batch state was an in-memory boolean and recursive blocks, with no queue recovery file.
- Timeout was explicitly excluded from batch retries; Retry-After was ignored.
- Lyrics fetching discarded HTTP/network distinctions, so an unsuccessful fetch looked like no lyrics.
- `PlayerLyrics.x` set `keepsSing=YES`, overriding the existing extrasHidden mic behavior.
- Settings used an overlay above the first drawer row and after the last settings row.

## Changes

AI context menus now route to the persistent per-song queue. Device translation engines keep
their existing behavior. The adapter shares the single-song request builder and JSON validation.
Both personal prompts are preserved; batch quality rules are appended and their multi-song
format is overridden by the per-song output contract. The old batch-size preference is retained
but no longer presented as a control for AI concurrency.

The queue uses atomic checkpoints with file fsync in Application Support and separately commits
each completed translation through the existing SQLite store. Concurrency is 2 by default,
configurable 1–3. Temporary failures have at most four attempts; HTTP 429 sets a global cooldown,
respects delta/date Retry-After and reduces concurrency after repeated limits. Authentication,
model, configuration and storage errors pause processing. Completed songs are checked against
the durable store before API calls and again before saving. Background entry pauses new work;
relaunch requires explicit Resume. In-flight results may still commit while paused.

Album/playlist contexts follow next_page_url; Liked Songs follows the documented saved-tracks
endpoint's next links, without a 50/100-song total cap. Pagination restricts credentials to the
original Spotify host, detects loops, and checkpoints the cursor. The UI also provides paged
album/playlist pickers and a link entry fallback. Existing translations and target-language songs
are skipped, missing Spotify lyrics are distinguished from network/JSON errors, and skip reasons
are retained in the queue report. Queue files contain identifiers, titles and errors, no API keys.

The drawer row moves below Settings and privacy when that native anchor is visible; the settings
row moves before About. Native cells are visually shifted to make room without changing their
data source. Unknown anchors retain a reachable footer fallback. The two-language subtitle is
added to the settings entry. This needs confirmation against the account's actual Spotify layout.

Selection lives in the actual SGRKaraokeView: long press, multiple toggles, dark rounded highlight,
dimmed neighbors, frozen following, cancellation and live switch changes. Meanings remain
available from their original bubble and the selection menu. Normal rendering is restored by
recreating line views when selection ends. The switch is off by default. The microphone now uses
the same extrasHidden state; its existing tucked setter disables touches and closes its slider.

## Native share evidence and limits

The actual 9.1.90 Spotify executable in the baseline IPA contains ShareLyricsService,
LyricsSharingPageView, LyricsShareSelectorPage, LyricsShareFormatViewController,
spotify:lyrics-share-selector and spotify:internal:lyrics:share:lines. These do **not** establish
a callable Swift API or the selected-line payload. No guessed private selector, feature-flag
override or fake Spotify image is shipped. Continue explicitly explains that native sharing is
unverified, keeps the selection, and offers original-text copy. **Native image sharing remains
incomplete**, not silently substituted with text sharing.

Apple's published MusicKit overview and Song.hasLyrics describe catalog/playback capabilities
and lyric availability; no supported native lyric-share controller for an arbitrary Spotify
selection was identified. Apple's user guide describes lyric sharing inside the Music app.
This is an investigation limit, not a proof of impossibility. No Apple Music option is exposed.

Primary references reviewed:
- https://developer.spotify.com/documentation/web-api/reference/get-users-saved-tracks
- https://developer.spotify.com/documentation/web-api/concepts/scopes
- https://developer.apple.com/documentation/musickit
- https://developer.apple.com/documentation/musickit/song/haslyrics
- https://support.apple.com/guide/iphone/show-song-credits-and-lyrics-iphb9bf483aa/ios

Liked Songs and library pickers require a usable Spotify session with the required scopes. A
mobile token is not assumed to have user-library-read; a denied response is reported. No live
account/API key or physical iPhone is available in this environment. Account flags, real native
share, end-to-end library access and live AI translation therefore remain unverified.
An AI request interrupted by process termination may have finished at the server without a local
result; generic compatible APIs offer no guaranteed exactly-once recovery for that case.

# Follow-up: incomplete translations reported on iPhone

The user confirmed the Karaoke microphone visibility fix. They also confirmed two failures in
the first V2.1 build: the selection flow could only display our unavailable-native-share alert,
and batch records could exist while playback showed few or no translated rows. The previous
simulator state assertions did not establish native sharing or end-to-end translation coverage.

This correction changes the actual persistence/playback path, not just the scheduler:

- A saved record is no longer sufficient to skip a batch song: its lines must cover the selected
  playback source. Empty/whitespace outputs and long, confidently foreign lines returned verbatim
  are incomplete even if the JSON array has the right length.
- Playback matches Unicode typography, punctuation, case and spacing without removing accents.
  Exact concatenation can join several saved rows for one displayed row. Ambiguous matches and
  splitting a translation across different displayed rows are deliberately left unresolved.
- Durable AI text takes priority over a community translation. Incremental saves merge and retain
  old source variants; the store and JSON/ZIP exports preserve the original input row metadata.
- Off-player jobs supply library title/artist metadata to the same source chain playback uses.
  A failed higher-priority source does not silently become a successful translation of another one.
- `Check saved results (no AI)` rechecks this queue's earlier saved/successful results without an AI
  call. `Translate missing saved lines` is explicit: it sends only uncovered rows of saved songs,
  keeps successful rows, and provides the full original song as narrative context. No prompts,
  credentials, target languages or translation records are reset.
- The copy-only feature is now labeled `Select and copy lyrics` and its action says `Copy`, with
  no unavailable-share dead end. Spotify native image sharing remains **unimplemented**, and
  Apple Music native sharing remains unverified. No fabricated images or guessed private calls.

New tests run the production SavedTranslations.m, SQLite store, KaraokeTiming.m and matching
helper on Mac Catalyst with synthetic lyrics and no API. Queue regressions verify explicit
rechecking and incomplete-saved results. These tests are not an iPhone or real-provider claim.
The new correction still requires actual-device verification, especially for the user's existing
affected JSON records, and cannot establish semantic translation quality from synthetic fixtures.
